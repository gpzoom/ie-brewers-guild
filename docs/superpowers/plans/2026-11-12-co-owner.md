# Co-owner Access Level Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a `co_owner` member role with the owner's rights (People, calendars, kitchen switch, Guild emails) minus control over co-owners and the owner, plus Change access, Leave, always-on People audit logging, roster display, and Member Guide updates.

**Architecture:** One new role value in `member_users.role` / `member_invites.role`, an "owner-level" SQL helper and TS helper used everywhere "owner" currently gates something, permission rules centralized in `src/lib/portal/people.ts` (pure, store-injected, unit-tested), and a service-role audit writer for People actions.

**Tech Stack:** TanStack Start (React, server functions), Supabase Postgres (RLS, SECURITY DEFINER SQL), Vitest, pgTAP (`npm run test:db`), Cloudflare Workers.

**Spec:** `docs/superpowers/specs/2026-11-12-co-owner-design.md`

## Global Constraints

- Role value is exactly `co_owner`; display label exactly "Co-owner".
- All on-screen text in US English (canceled, color, check the box).
- **Staging and production share ONE Supabase database.** The migration must keep the live (main-branch) code working: additive only, no renames, no dropped values. `supabase db push` requires the site owner's explicit go-ahead (Task 9). `npm run test:db` runs inside rolled-back transactions on that shared DB; it is allowed.
- Every People write is checked in the Worker before the service-role client is used; SQL/RLS enforces calendar, kitchen and draft rights.
- Only the owner (including a Guild admin editing as them, whose portal role is `"owner"`) may invite, resend, cancel, remove or change a co-owner or a pending co-owner invite.
- Nobody but the Guild removes or changes the owner. The business manager of a one-manager business can never be made a co-owner of a handed-off location.
- Hand-off and take-back turn the location's co-owners into Full editors and cancel its pending co-owner invites.
- Guild emails to "the member" go to the owner and every co-owner, one separate email each; business-manager editor rows never receive them.
- Every People change is audit-logged, whoever makes it, with the real signed-in user as actor.
- `npm run build` before every push to staging. Locally it needs placeholder `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_GOOGLE_MAPS_API_KEY` set in the shell for that one command (never written to a file).
- `/admin` (Edit as them) must keep working: a Guild admin there has owner rights.

## Review Focus

1. **A co-owner tries to act on a co-owner via a side door.** Re-inviting an address that has a pending Co-owner invite as an editor (which would quietly downgrade it), or resending/canceling it, must be refused for a co-owner. Tests in Task 3.
2. **Live (main) code meets a `co_owner` row before the merge.** `listPortalMemberships` on main drops unknown roles, so a co-owner simply can't sign in on the live site yet; nothing may crash. Task 9 says to test only with sample members on staging until the merge.
3. **Hand-off of a location whose co-owner is also invited elsewhere, or a take-back with a pending co-owner invite.** Rows are demoted and invites canceled atomically, in the same SQL function. pgTAP in Task 1.
4. **A member with no owner row but a co-owner** (e.g. after a take-back race). Emails still go to the co-owners; the fallback to the earliest row applies only when neither exists. Test in Task 6.
5. **Someone leaves or is demoted while their page is open.** Their next request is denied by the server, not just hidden in the UI. Covered by the server checks in Task 5. No new test needed beyond Task 3's rule tests.
